# Enhanced Route-Order Local Search

## Objective

Extend the existing technician scheduling module with two route-order operators:

- **Intra-route swap:** exchange the positions of two tasks assigned to the same technician-day.
- **2-opt:** reverse a contiguous section of a route to explore a different visit order.

The script begins with the saved relocation-local-search output when available; otherwise, it uses the route-insertion schedule. This makes the experiment an additional optimization pass, not a replacement for the existing baselines.

## Feasibility safeguards

Every candidate route is reevaluated using the module's shared route evaluator. A move is accepted only when:

1. The complete route remains feasible with task time windows, technician shift bounds, travel times, and final return-to-depot travel.
2. Total travel decreases by more than the configured numerical tolerance.
3. The set of assigned tasks is unchanged.

The final output is re-evaluated before it is saved. The algorithm is a bounded first-improvement heuristic; it is not guaranteed to find a global optimum.

## Run

From the module root:

```powershell
python -m py_compile src/improve_local_search_moves.py
python src/improve_local_search_moves.py
```

Expected local outputs:

- `data/processed/enhanced_local_search_routes.csv`
- `data/processed/enhanced_local_search_task_status.csv`
- `data/processed/enhanced_local_search_summary.json`

The script requires the prepared tasks, technicians, scheduler outputs, and travel matrices generated by the existing pipeline. These data files are ignored by Git, so a fresh clone must first follow the data preparation instructions in the module README.

## Evaluation

Compare the summary's initial and final travel minutes, accepted moves, route count, and assigned-task coverage with the previous validated schedule. Do not claim improvement until the script is run on the local data and the output is checked. Because route feasibility is reevaluated with the same source duration field used by the existing benchmark, this validates internal consistency on the benchmark, not real-world performance on plumbing jobs.

## Limitation

The benchmark is telecommunications field-service data. The results are a research prototype and should not be represented as measured savings for an actual plumbing business.
